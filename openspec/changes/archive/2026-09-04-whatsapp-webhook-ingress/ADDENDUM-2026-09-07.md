# Addendum (2026-09-07): post-archival correction to 0004_tenant_resolver.sql

This capability was archived 2026-09-04 with verify PASS, 0 CRITICAL, 0 WARNING.
On 2026-09-07, while running this project's migrations for the first time
against a real (non-superuser) Neon database — as part of testing the
`admin-dashboard` UI — `0004_tenant_resolver.sql`'s `ALTER FUNCTION
public.dirus_resolve_broker_id(text) OWNER TO dirus_tenant_resolver;`
statement failed with `permission denied for schema public`.

**Root cause**: Postgres requires the *new* owner of an object to hold
`CREATE` privilege on the object's schema at the moment of ownership
transfer, unless the executing role is a true superuser. CI's
`pgvector/pgvector:pg17` service container runs as an actual Postgres
superuser, which bypasses this check unconditionally — so this defect was
present in the archived migration from day one and could never have been
caught by CI. It was invisible until the first real (non-superuser) Neon
connection ran it.

**Fix** (commit `f82c669`, this session, explicitly approved by the project
owner before being applied — see that commit's message for the full
before/after SQL): bracketed the `ALTER FUNCTION ... OWNER TO` statement
with a temporary `GRANT CREATE ON SCHEMA public TO dirus_tenant_resolver`
/ `REVOKE CREATE ON SCHEMA public FROM dirus_tenant_resolver` pair, so the
new owner holds `CREATE` only for the instant the transfer requires it,
then loses it again — the role's standing privilege set (`USAGE` only) is
unchanged from what this capability's own design specified.

**Why this was edited in place rather than shipped as a new migration**:
at the time of the fix, `0004_tenant_resolver.sql` had never been
successfully applied to any real, persistent database — every prior
application was either CI's ephemeral superuser container (destroyed every
run) or had failed outright on this exact statement. There was no deployed
catalog anywhere that reflected the pre-fix text and could diverge from it.
This is the one condition under which amending an archived migration is
safe; it does not hold for any migration once a real environment has
successfully applied it, which is exactly why this project's convention —
reaffirmed by `fix-chatwoot-tenant-resolution` (F2.1), the next change to
touch this same function — treats `0004` as immutable from that point
forward and ships all further correction as new, forward-only migrations
(`0007_chatwoot_account_resolution.sql`).

**Scope note**: the identical fix was applied in the same commit to
`0006_broker_auth.sql` (archived under `admin-dashboard`/C1,
2026-09-07) — see that capability's own addendum.

No table, column, RLS policy, or grant scope changed. `dirus_resolve_broker_id`'s
security envelope (`SECURITY DEFINER`, owned by `dirus_tenant_resolver`,
`SET search_path = ''`, schema-qualified body, bare-`uuid` return, no
`status` predicate) is unchanged — verified directly against the current
file at the time of this addendum.
