## Migration: `packages/db/migrations/0006_broker_auth.sql`

Generated via `drizzle-kit generate` (schema-driven, since this migration adds
real tables/columns, unlike 0004's pure `--custom` role/function migration)
from the updated `src/schema/{broker_users,magic_link_tokens,sessions}.ts`,
then hand-extended with the RLS/grant/function sections design.md D-A/D-H
specify, mirroring 0004's resolver-function pattern and 0002's RLS shape
exactly. One deliberate, documented deviation from drizzle-kit's default
output:

1. **The generated `ALTER TABLE "broker_users" ADD CONSTRAINT
   "broker_users_email_key" UNIQUE("email")` line was rewritten as
   `CREATE UNIQUE INDEX "broker_users_email_key" ON public.broker_users
   ("email")`.** Both produce an equivalent unique index in Postgres, but the
   `CREATE UNIQUE INDEX` form is this repo's established convention for a
   hand-reasoned-about index shape (`0005_policy_number_unique_index.sql`
   uses the identical form), and matches tasks.md task 1.1's literal wording
   for the structural test. The Drizzle schema (`broker_users.ts`) still
   declares the column via `unique("broker_users_email_key").on(table.email)`
   — `drizzle-kit check` reports zero drift either way since both forms
   satisfy the same schema-level uniqueness declaration.

The down path (task 1.3) is a documented comment block at the end of the
file, in the exact order design.md D-H specifies: `REVOKE EXECUTE` (x3) →
`DROP FUNCTION` (x3) → `DROP POLICY` (the three `tenant_resolver_lookup`
policies, then the two `tenant_isolation` policies) → `REVOKE SELECT` (the
column grants, x3) → `REVOKE` the owner's membership → `DROP TABLE` (both new
tables) → `DROP INDEX`/`DROP COLUMN` (the email index and column). It is not a
second executable script — this migration sequence has no down-runner,
consistent with 0000-0005.

## Deviation from task 1.4's literal wording: folded into `live-broker-auth.test.ts`, not `rls-catalog-guard.test.ts`

Task 1.4 says "extend `packages/db/test/migrations/rls-catalog-guard.test.ts`
with the per-table guards design D-A's assertion 4 names." That file applies
migrations into a randomly-named **throwaway schema** (never `public`), which
is incompatible with `0006_broker_auth.sql`'s three function bodies —
they deliberately hardcode `public.broker_users` / `public.magic_link_tokens`
/ `public.sessions` (the search_path-hijack defense itself; rewriting that
qualification to point at a throwaway schema would defeat the property under
test, exactly the same incompatibility `live-tenant-resolution.test.ts`'s file
header documents for `0004_tenant_resolver.sql` and F2's own task 1.4).

This project has already established the house convention for this exact
situation: `live-tenant-resolution.test.ts`'s header states "Task 1.4
explicitly allows folding its catalog guard into a sibling file rather than
extending `rls-catalog-guard.test.ts` verbatim — this file IS that sibling."
This batch's `admin-dashboard` task 1.4 text does not repeat that explicit
allowance in as many words, but the underlying technical constraint is
identical, so the same resolution was applied: D-A's assertion-4 catalog
checks (policy `TO` clause, function ownership/`SECURITY
DEFINER`/`proconfig`, `EXECUTE` grantee, `pg_auth_members` membership guard)
live inside `live-broker-auth.test.ts`'s own "4. catalog guard" `describe`
block, which needs the exact same dedicated-database fixture assertion 1/2/3/5
require anyway — building a second, disjoint fixture just to host the
catalog-only checks would duplicate `beforeAll`/`afterAll` for no isolation
benefit. `rls-catalog-guard.test.ts` itself was not touched.
